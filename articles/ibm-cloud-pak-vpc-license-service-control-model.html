IBM Cloud Pak VPC Licensing: How to Build a Control Model Around IBM License Service

Cloud Pak licensing is not just PVU with a new label. VPC ratios, container reporting, IBM License Service, and OpenShift operations change the SAM control model.

Executive View

As IBM workloads transition from virtual machines to containerized microservices (using Red Hat OpenShift and Kubernetes), the traditional Processor Value Unit (PVU) licensing model is being replaced by Virtual Processor Core (VPC) metrics. This architectural shift requires a completely new compliance approach.

Practitioner Notes

Senior perspective: "VPC licensing on containers seems flexible, but IBM's sub-capacity rules are extremely rigid. If your cluster is not configured with IBM License Service (ILS), or if your ILS reporting has gaps, IBM can demand full-capacity physical licensing during audits."

This article outlines the operational controls required to manage IBM Cloud Pak licensing, configure the IBM License Service (ILS) correctly, and defend your containerized sub-capacity positions.

Senior Takeaway

Do not assume that container orchestrators (like Kubernetes or OpenShift) automatically manage licensing. Kubernetes restricts resource allocation, but IBM licensing is determined by peak active vCPU usage over a historical 90-day window, tracked at the container level.

What Changed

Under traditional models, sub-capacity PVU calculations required deploying and maintaining the IBM License Metric Tool (ILMT) at the operating system level. For containerized Cloud Pak workloads, IBM introduced the IBM License Service (ILS), which runs inside Kubernetes clusters to track vCPU usage directly.

Dimension Traditional VM Model (ILMT) Container Model (ILS) Operational Shift
Tracking Agent ILMT agents installed on every VM OS IBM License Service pod per cluster Reduces operating system management overhead.
Measurement Unit Processor Value Units (PVU) based on core factors Virtual Processor Cores (VPC) at pod level Decouples licensing from physical core factor multipliers.
Peak Calculation Full virtual machine capacity peak Actual active pod CPU limits and allocations Allows granular scaling but requires active pod resource limits.

The VPC Model & Cloud Paks

IBM Cloud Paks bundle multiple IBM applications (e.g., WebSphere, MQ, Db2, API Connect) into unified, industry-specific suites (e.g., Cloud Pak for Integration, Cloud Pak for Data). These suites are licensed using Virtual Processor Cores (VPC) that represent a pooled capacity allocation.

The Shared-Pool Trap

Because Cloud Paks allow you to deploy different bundled products under a single VPC license pool, developers can inadvertently consume the entire company-wide VPC entitlement by deploying highly resource-intensive components without budget approvals.

IBM License Service (ILS)

The IBM License Service (ILS) is a lightweight collector pod deployed via a Kubernetes operator. It automatically scans all namespaces, identifies active IBM container images, and records the maximum allocated vCPU cores. Deploying ILS is a strict requirement for sub-capacity container licensing.

Practitioner Notes

"If you run containerized IBM software (like MQ or WebSphere) on OpenShift without having the IBM License Service active in the cluster, IBM auditors will calculate your compliance requirements using the full physical core capacity of all worker nodes in the cluster."

Sub-Capacity Container Rules

To qualify for container sub-capacity licensing (which allows you to pay only for the virtual cores allocated to your IBM pods rather than the entire physical cluster), you must configure your deployments to meet IBM's compliance criteria.

Requirement Technical Action Failure Pattern
Active ILS Pod Ensure the IBM License Service pod is running continuously in every cluster. Workloads are deployed on a new cluster before ILS is installed.
Resource Limits Enforce mandatory CPU limits on all IBM pods in the Kubernetes spec. Failing to set pod limits, causing IBM to count the full node capacity.
90-Day Retention Extract and archive ILS audit snapshots every 90 days. Failing to retain history, violating sub-capacity record-keeping rules.

VPC Ratios & Bundling

Different bundled components in a Cloud Pak require different conversion ratios. For example, deploying one VPC of IBM MQ might consume only 0.5 VPC of your Cloud Pak for Integration pool, while deploying one VPC of API Connect consumes 1.0 VPC. These ratios must be modeled to track actual pool usage.

Cloud Pak Suite Bundled Component Conversion Ratio (Component to Pak) Calculated VPC Consumed
Cloud Pak for Integration IBM MQ 1:2 (0.5 Pak VPC per core) 10 MQ cores = 5 Pak VPCs consumed
Cloud Pak for Integration IBM API Connect 1:1 (1.0 Pak VPC per core) 10 API Connect cores = 10 Pak VPCs consumed
Cloud Pak for Integration IBM App Connect Enterprise 2:1 (2.0 Pak VPC per core) 10 App Connect cores = 20 Pak VPCs consumed
Cloud Pak for Data IBM Db2 Enterprise Edition 1:1 (1.0 Pak VPC per core) 10 Db2 cores = 10 Pak VPCs consumed

ILS Data Collection API

The IBM License Service exposes REST API endpoints to retrieve your peak VPC usage and generate compliant audit reports. You can write scripts to query these endpoints and pull the data directly into your central SAM tools.

REST API Call to Retrieve ILS Peak VPC Usage
# Pull peak VPC usage for the last 90 days via ILS API
curl -k -H "Authorization: Bearer " \
  https://:/v1/metric?startDate=2026-02-01&endDate=2026-05-01
# Response contains: productCode, productName, metricName, maxMetricValue

ILS & ILMT Coexistence

Most large enterprises run a hybrid model: legacy virtual machines monitored by ILMT, and containerized clusters monitored by ILS. Reconciling these dual data sources requires integrating both platforms into your Flexera or ServiceNow system.

The Double-Reporting Trap

Ensure that virtual machine hosts running Kubernetes nodes are excluded from ILMT scanning, or marked as excluded, to prevent double-counting the CPU cores in both your VM-based PVU reports and your container-based VPC reports.

Practitioner Q&A

What happens if a pod runs without a CPU limit specified?

Under IBM's sub-capacity rules, if a containerized IBM product pod is deployed without explicit resource limits in the Kubernetes pod specification, the IBM License Service will calculate the required cores using the maximum capacity of the Kubernetes worker node where that pod is currently scheduled. This can inflate your VPC requirements instantly.

How does ILS calculate VPC when pods move between worker nodes?

The IBM License Service aggregates the peak concurrent VPC usage within each cluster. If Kubernetes reschedules a pod to a different worker node, the service filters out duplicates and reports only the concurrent peak, avoiding double-counting due to migration.

Are Red Hat OpenShift Core licenses included in Cloud Paks?

Yes. Many IBM Cloud Pak licenses (such as Cloud Pak for Integration or Data) are bundled with "Red Hat OpenShift Container Platform" entitlements. These bundled OpenShift entitlements are restricted and can only be used to host the IBM Cloud Pak components, not general third-party applications.

Quick Revision Cheat Sheet

ILS Mandate

ILS must run continuously in every container cluster. Missing service = Full-capacity physical host risk.

VPC Ratios

MQ is 0.5 Pak VPCs per core, App Connect is 2.0 Pak VPCs per core. Ratios must be managed to avoid pool exhaustion.

90-Day Peak

License usage is determined by the peak concurrent allocated vCPUs over a 90-day window, not the average usage.

Resource Limits

Mandatory control: Enforce CPU resource limits on all IBM pod specs. Unrestricted pods trigger full-node calculations.
